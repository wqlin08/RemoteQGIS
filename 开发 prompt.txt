RemoteQGIS  项目开发任务
1. 项目背景与目标
开发一个开源 QGIS 插件，实现跨设备、跨操作系统、跨网络的远程 GIS 工作空间。项目的主要使用场景为 macOS 客户端与 Windows 工作站之间的远程协同，两台设备可能位于不同单位，使用不同的网络和 IP 地址。
项目参考 VS Code Remote SSH 的工作模式，将 GIS 软件的交互界面与实际数据存储、计算资源分离。用户在 macOS 上使用原生 QGIS 完成日常 GIS 操作，而原始数据、QGIS 主项目、矢量编辑成果、空间分析结果及其他输出文件均存储在 Windows 工作站。
项目不采用传统远程桌面方案，不通过持续传输远端屏幕画面实现交互，而是通过本地 QGIS 渲染、远程数据按需访问、操作指令传输、编辑事务同步及远程计算实现协同。
最终产品为同一个 QGIS 插件，分别安装在两台设备的 QGIS 中，通过 Host Mode 和 Client Mode 区分运行职责。Windows 端启动 QGIS 并开启 Host Mode 后，macOS 客户端应当能够独立完成整个 GIS 工作流程，无需用户频繁操作 Windows。
项目面向单客户端、单工作站的使用场景，暂不考虑多人协同编辑、无人值守运行、云平台部署、分布式计算集群及复杂的用户权限管理体系。
2. 开发环境与版本管理
主要开发工作在 macOS 上进行，使用 Python、PyQGIS 和 QGIS 自带的 Qt/PyQt 环境开发插件。代码需要兼容 macOS 和 Windows，最终在两台设备的 QGIS Desktop 中运行。
开发前检查当前 macOS 的 QGIS 版本、Python 版本、Qt 版本、GDAL 环境和可用的 PyQGIS API，明确插件支持的 QGIS 版本范围。不得直接假定系统 Python 环境与 QGIS 内置 Python 环境一致，也不得随意修改 QGIS 自带的 Python 或 GDAL 依赖。
使用 Git 进行完整的版本管理。在项目初始化时建立 Git 仓库、README、CHANGELOG、.gitignore、项目许可证、开发文档和测试目录。项目采用与 QGIS 及所集成开源组件许可证兼容的开源协议，正式确定许可证之前应当完成依赖协议核查。
采用阶段式开发方式，每完成一个独立功能模块并通过测试后进行 Git Commit。提交信息应明确说明功能变更、修复内容及涉及的模块。重大功能调整使用独立分支，验证通过后再合并至主分支。每个稳定开发阶段通过 Git Tag 建立可回滚的版本节点，例如 v0.1.0、v0.2.0 和 v0.3.0。
修改已有稳定功能之前检查 Git 工作区状态，保留用户已有修改。不得擅自执行 git reset --hard、强制推送、清理未跟踪文件或其他可能导致代码丢失的操作。发现功能退化时，应通过版本差异、测试结果和运行日志定位问题，再决定修复或回滚策略。
Git 仓库不得包含大型遥感影像、测试生成的业务数据、访问令牌、连接凭据、运行缓存和系统临时文件。
3. 整体系统架构
采用远程主项目与本地代理项目架构，即 Remote Master Project and Local Proxy Project。
Windows 端运行实际 QGIS 主项目，持有真实数据图层、数据源路径、项目状态和计算结果。macOS 端建立与远端主项目对应的轻量化代理项目，负责用户交互、地图渲染、临时编辑和操作指令生成。
系统由 Client Plugin、Host Plugin 和 Host Service 三部分组成。
Client Plugin 运行于 macOS QGIS 中，负责远程文件浏览、数据导入、远程图层管理、本地地图渲染、缓存管理、矢量编辑、属性编辑、远程 Processing 算法调用及任务状态显示。
Host Plugin 运行于 Windows QGIS 中，负责实际项目管理、真实图层加载、图层状态修改、编辑事务执行、数据保存和处理结果加载。
Host Service 负责网络通信、远程文件访问、遥感影像服务和计算任务管理。根据实际依赖和线程安全要求，可以由 Host Plugin 启动独立后台进程。后台服务随 Host Mode 启动和停止，不要求实现无人值守运行。
Client Plugin 和 Host Plugin 应当共享通信协议、数据模型、错误定义、消息序列化及连接管理等公共模块。
Windows 端作为项目状态和业务数据的唯一权威来源。macOS 端允许保留影像瓦片、临时矢量数据、编辑缓冲区及必要的恢复记录，但不要求用户下载和维护完整原始数据。
4. 开源技术选型与复用原则
本项目不从零实现成熟的网络通信、内网穿透、空间数据读取、遥感影像渲染和 GIS 算法。优先使用经过长期维护、具有完善文档和合理开源许可证的现有技术。
开发前应实际调查相关项目的官方文档、GitHub 仓库、维护状态、许可证、Python 依赖、平台兼容性及接口能力，形成技术选型文档。以下为初始候选技术体系，允许根据实际调查及测试结果调整。

5. 双端连接与服务管理
同一个插件提供 Host Mode 和 Client Mode 两种运行模式。
Windows 端选择 Host Mode 后，可以配置共享目录、监听地址、服务端口和访问认证信息，并启动远程服务。插件负责检测所需运行环境和依赖，在必要时启动独立的后台服务进程。
macOS 端选择 Client Mode 后，通过远端 IP 地址或主机名、端口和访问令牌连接工作站。
跨网络连接优先使用 Tailscale，不自行开发 NAT 穿透、P2P 网络、加密隧道和中继服务器。插件应当基于普通 TCP/IP 网络接口工作，使其同样兼容局域网、其他 VPN 或 WireGuard 网络。
网络通信采用 HTTP API 与 WebSocket 相结合的方式。HTTP 主要负责文件列表、图层元数据、影像数据、算法参数及其他请求响应式操作；WebSocket 主要负责项目状态变化、图层更新、编辑确认、任务进度及实时通知。
客户端网络请求必须异步执行，不允许网络等待阻塞 QGIS 主线程。实现连接状态检测、请求超时、心跳检测、异常反馈和断线重连。
所有远端文件操作必须限制在用户授权的共享目录内，服务需要验证路径、访问令牌和操作权限。不得直接暴露任意 Python 代码执行、任意系统命令执行或无访问控制的文件读取接口。
6. 远程文件浏览与数据导入
远程文件浏览是项目的核心功能之一。
在 macOS QGIS 中实现原生风格的远程文件浏览器，允许用户访问 Windows 工作站授权共享的磁盘目录、文件夹和文件。界面应当支持路径输入、目录导航、返回上一层、刷新、文件类型筛选、多选、双击导入和拖拽导入。
优先研究 QgsDataItemProvider、QgsBrowserGuiModel、QgsCustomDropHandler 等 QGIS API，将远程数据浏览功能集成到 QGIS 原生 Browser Panel。必要时提供独立的远程文件选择窗口。
用户在 macOS 中点击远程数据导入按钮时，文件选择窗口展示的应当是 Windows 文件系统中的数据，而不是 macOS 本地文件系统。
当用户选择或拖入一个远端 TIFF、Shapefile、GeoPackage 或其他受支持的数据文件时，macOS 端向 Windows 发送文件路径及导入指令。Windows QGIS 首先使用 PyQGIS 加载真实图层，随后返回图层唯一标识、数据类型、坐标参考系、空间范围、字段信息、波段信息及渲染参数。macOS QGIS 根据这些信息自动建立相应的代理图层。
禁止将完整大型遥感影像下载至 macOS 作为默认的数据导入实现，也不得要求用户提前在 Windows QGIS 中手动加载数据。
远程文件浏览器还应当支持新建目录、创建数据文件、重命名及经过明确确认的删除操作，并为远程算法输出和项目保存提供统一的路径选择接口。
7. 远程遥感影像访问与高性能渲染
遥感影像浏览是影响跨网络使用体验的主要性能环节，应当作为项目的重点研发及测试内容。
项目采用分块读取、多分辨率影像金字塔、动态瓦片服务及本地缓存相结合的方式，使 macOS 仅获取当前地图视野所需的数据。
优先使用 GDAL、Rasterio 和 TiTiler 实现远程栅格读取及动态影像瓦片生成。对于适合 COG 格式的数据，可以使用 HTTP Range 请求读取必要的数据块。对于现有普通 GeoTIFF，应当支持直接读取，并根据影像组织方式选择合适的概览或缓存策略，不得要求用户在导入前手动转换所有数据。
影像服务需要支持坐标参考系转换、空间范围查询、波段选择、RGB 组合、灰度显示、数值拉伸、NoData 处理及必要的重采样方式。
客户端优先使用 QGIS 原生 XYZ、WMTS、WMS 或其他适合的栅格数据提供器加载远程图层，避免重复开发地图渲染引擎。根据实际技术验证结果，确定是否需要自定义栅格数据提供器或独立的远程像元查询接口。
影像显示数据与科学计算数据需要明确区分。用于浏览的 JPEG、PNG 等渲染瓦片不得作为真实遥感像元值参与高程查询、光谱分析和 GIS 数值计算。原始像元读取必须通过真实栅格数据访问或远端查询接口完成。
实现内存缓存、持久化磁盘缓存、相邻区域预加载、异步并行请求、过期请求取消和渐进式显示。缓存键需要包含数据源版本、波段组合、渲染参数、坐标系及瓦片索引，避免影像更新或渲染方式变化后显示错误的历史缓存。
地图平移、缩放及矢量化交互不能依赖远端屏幕刷新。优先复用已经缓存的瓦片，并在后台获取缺失的数据。
禁止将持续截取和传输 Windows QGIS 地图画布作为主要遥感影像显示方案。
8. QGIS 项目与图层状态同步
Windows QGIS 持有真实主项目。macOS 客户端连接成功后，自动读取远端项目结构，并构建对应的本地代理项目。
同步内容包括图层唯一标识、图层名称、数据源信息、图层顺序、分组结构、可见性、透明度、坐标参考系、渲染样式及必要的项目元数据。
用户可以在 macOS 中添加、删除、重命名、排序、分组和修改图层样式。所有属于项目持久化状态的修改都应当同步到 Windows QGIS。
建立稳定的远端图层 ID 与本地代理图层 ID 映射机制，避免依赖图层名称识别数据。协议应支持完整项目状态初始化和增量状态更新，并避免双端事件监听引起循环同步。
支持从 macOS 发起远端 QGIS 项目创建、打开、关闭、保存及另存为操作。最终 .qgs 或 .qgz 文件必须写入 Windows 工作站，并使用真实的远端数据源路径。
地图视野可以在 macOS 独立流畅地操作，同时通过异步、节流或防抖方式将地图中心、比例尺、显示范围及旋转角度同步至 Windows。
所有涉及 QgsProject、QGIS GUI 和非线程安全 QGIS 对象的操作均需要通过适当的 Qt 主线程调度执行。禁止在 FastAPI 网络线程中直接修改 QGIS GUI 或跨线程访问不安全的图层对象。
9. 远程矢量化与属性表编辑
用户应能够直接在 macOS QGIS 中使用原生矢量编辑工具，包括点、线、面绘制，节点编辑，捕捉，几何修改，要素删除，属性表编辑，字段修改，字段计算及撤销重做。
优先使用 QGIS 原生 QgsVectorLayer、编辑缓冲区及相关信号实现本地交互，不重新开发矢量化工具和属性表界面。
第一版需要支持 Windows 端已有的 Shapefile 和 GeoPackage 数据，并允许用户在 macOS 中指定远端保存路径、新建矢量图层和定义字段结构。
远端数据可以通过可编辑的本地代理图层提供给 QGIS。对于小型矢量数据，可以读取必要的完整要素；对于大型矢量数据，应当研究基于空间范围和属性条件的按需访问方式。
本地编辑需要具备稳定的全局要素标识，与远端 FID 建立明确映射。不得假定不同设备上的临时要素 FID 一致，也不得依赖 Shapefile 在所有编辑操作之后保持 FID 不变。
鼠标移动、节点绘制、捕捉和编辑预览由 macOS 本地完成。用户保存编辑时，将新增要素、删除要素、几何变化、属性变化及字段变化作为明确的编辑事务提交给 Windows，由 Windows 执行实际数据修改。
远端确认保存成功后，macOS 才能清除对应的待提交编辑状态。保存失败或网络中断时，应保留未提交内容并提供明确的错误反馈、重试和恢复能力。
编辑事务需要考虑重复请求、临时要素 ID 更新、保存失败、撤销重做及数据源变化等情况。对不具备完整原子事务能力的数据格式，必须采用适当的验证、备份或恢复策略。
当采用局部矢量加载时，需要确保编辑范围内的捕捉、邻接要素、拓扑关系及属性查询正确。不得因局部加载而破坏实际数据的空间关系。
Windows 作为唯一业务数据写入端，第一版不要求支持两台设备同时修改同一图层的多人协同冲突处理。
10. 远程 GIS Processing 计算
在 macOS QGIS 中注册自定义 Remote Processing Provider，并将远端工作站可执行的算法集成至 QGIS Processing Toolbox。
连接 Windows 后，客户端获取远端已经安装和可用的 Processing 算法列表、算法 ID、输入参数类型、输出参数类型及相关元数据。
优先支持常见的 QGIS Native 和 GDAL 算法，包括栅格裁剪、重投影、重采样、波段运算、栅格计算、地形分析、矢量叠加、缓冲区、几何处理、空间统计及格式转换。
用户在 macOS 设置算法参数时，应能够直接选择远端文件、远端真实图层及远端输出路径。客户端代理图层 ID 需要自动转换为远端真实数据源或图层引用。
算法参数通过网络发送至 Windows 工作站，由 processing.run()、QgsProcessingAlgRunnerTask、qgis_process 或经过验证的独立计算进程执行。根据算法的线程安全属性和运行环境选择适合的执行方式。
实际计算使用 Windows 工作站的 CPU、内存及磁盘资源。支持 GPU 的自定义算法可以调用工作站 GPU，但不要求将普通 QGIS 算法强制转换为 GPU 计算。
客户端提供任务状态、实时进度、运行日志、异常信息和取消任务功能。任务完成后，Windows QGIS 自动加载实际结果图层，macOS 自动创建相应代理图层。
不得默认将输入数据传输至 macOS 后在本地完成计算。所有远程 Processing 任务的最终输出均保存在 Windows。
初期应选择一组明确支持的算法完成参数映射和端到端测试，然后逐步扩展算法覆盖范围。不能假定所有 QGIS Processing 算法和第三方算法提供器都具有相同的远程执行条件。
11. 网络性能及缓存优化
项目从开始便面向广域网环境设计，不假定两台设备处于同一局域网。
充分考虑网络往返延迟、工作站上传带宽、丢包率、连接抖动、直连及中继连接等条件。所有允许在本地完成的交互尽量在 macOS 完成，尽量减少需要同步等待远端响应的操作。
不逐次传输鼠标移动事件，不重复传输完整项目状态，不重复获取未发生变化的图层元数据，不重复下载已经缓存的影像瓦片。
实现连接诊断功能，展示当前连接状态、网络往返延迟、有效数据传输速率、请求失败率、瓦片缓存命中率和地图加载耗时。结合 Tailscale 的诊断信息判断当前网络连接状况。
通过实际测量评估不同网络条件下的表现，包括冷缓存、热缓存、连续地图平移、快速缩放、波段切换、矢量编辑和计算任务执行。
初始性能测试可以采用 10、30、50、100 和 200 ms 的模拟往返延迟，以及不同有效上传带宽，分析系统性能随网络条件变化的情况。
主要性能指标包括地图交互帧耗时、首次影像显示时间、完整视图加载时间、瓦片缓存命中率、编辑提交确认时间、网络传输量、内存占用和后台任务资源占用。
性能目标是保证本地交互不被网络等待阻塞，并尽可能降低新区域影像的加载延迟。不得使用未经测试的固定延迟或帧率承诺作为开发结果。
12. 插件界面设计
插件界面遵循 QGIS 原生桌面软件设计风格，保持简洁、清晰及一致性。
不另行开发脱离 QGIS 的独立 GIS 界面。优先将功能集成到 QGIS 工具栏、菜单、Browser Panel、Dock Widget、Processing Toolbox 和状态栏。
主要界面包括连接管理窗口、Host Mode 配置窗口、Client Mode 配置窗口、远程文件浏览器、远程路径选择窗口、远程任务管理面板和连接诊断面板。
远程图层需要具有明确的状态标识，使用户能够区分已连接、加载中、存在未保存编辑、等待远端确认、连接中断和发生错误等状态。
尽量保留 QGIS 原生操作习惯，使用户无需学习一套全新的地图操作和矢量编辑工具。
插件最终通过标准 QGIS ZIP 插件包进行安装。提供依赖检测、环境配置及必要的安装说明。Host Service 的启动、停止和状态检测应尽可能集成至插件内部，避免用户每次使用时手动启动多个后台程序。

14. 分阶段开发计划
V0.1 — 项目初始化与双端通信
完成 Git 仓库初始化、项目目录组织、QGIS 插件基本框架、Host Mode 和 Client Mode 界面、依赖环境检测、HTTP API、WebSocket 通信、连接认证及基本日志管理。
实现两台 QGIS 的连接测试，能够读取远端 QGIS 版本、主机基本信息及当前项目名称。
V0.2 — 远程文件系统与数据导入
实现远程目录浏览、文件筛选、路径选择、双击导入和拖拽导入。
完成 macOS 发起导入操作、Windows QGIS 加载实际数据、返回图层信息以及 macOS 创建初步代理图层的完整工作流。
重点确保用户不需要提前在 Windows 导入数据。
V0.3 — 高性能遥感影像浏览
完成远程栅格数据服务、动态瓦片、影像金字塔、坐标系转换、波段组合、本地持久化缓存、异步请求及预加载机制。
完成真实大型遥感影像的跨网络浏览测试，并分析地图平移与缩放性能。
V0.4 — 项目与图层管理
完成远端项目创建、打开、保存、关闭和另存为操作，实现图层增删、排序、分组、渲染样式及地图视野同步。
建立稳定的图层映射机制、项目状态版本及增量同步协议。
V0.5 — 矢量化与属性编辑
完成远程矢量文件创建、矢量代理图层、几何绘制、节点修改、捕捉、属性表编辑、字段管理、撤销重做及远端编辑事务提交。
重点验证 GeoPackage 和 Shapefile 格式的数据一致性，以及网络异常情况下未提交编辑的恢复能力。
V0.6 — 远程 GIS 计算
完成 Remote Processing Provider、算法发现、参数转换、远端路径选择、计算任务执行、进度反馈及结果图层自动加载。
验证常用栅格和矢量算法实际使用 Windows 工作站计算资源，并确保输出文件保存在远端。
V0.7 — 性能优化与稳定性测试
对网络通信、影像服务、本地缓存、编辑事务及计算任务进行系统性性能分析。
完成不同网络条件下的测试，修复内存泄漏、界面阻塞、重复同步、缓存失效、连接恢复及错误处理等问题。
V1.0 — 正式发布
完成跨平台安装测试、依赖管理、标准 QGIS 插件 ZIP 打包、用户文档、部署说明、开发者文档、测试报告及开源许可证审查。
每个阶段完成后必须执行相关测试，更新 CHANGELOG，记录已实现功能和遗留问题，提交 Git 并建立稳定版本标签。当前阶段尚未稳定时，不应无计划地大量开发后续功能。
15. 测试与验收要求
自动化测试覆盖网络消息、数据模型、远程路径验证、图层映射、缓存索引、编辑事务和算法参数转换等核心逻辑。
在 macOS 开发环境中可以通过本地模拟服务、独立进程或测试数据完成单元测试和初步集成测试。涉及真实 Windows 文件系统、Windows QGIS、跨网络通信及远端计算资源的功能必须进行实际双端测试。
最终应完成以下端到端验收工作流：
Windows 工作站启动 QGIS，开启 Host Mode。macOS 打开 QGIS 并连接工作站，在远程文件浏览器中访问 Windows 的数据目录，选择一幅大型遥感影像并拖入地图画布。Windows QGIS 自动加载实际影像，macOS 自动显示对应图层。
用户在 macOS 中连续进行地图平移和缩放，在远端目录中新建 GeoPackage 矢量数据，绘制多个多边形，修改几何及属性并保存编辑。随后在 Remote Processing Toolbox 中执行影像裁剪、重投影或其他空间分析算法，将结果输出至 Windows 指定目录。处理完成后，双端 QGIS 自动加载结果。
最后在 macOS 点击保存项目，Windows 写入实际 QGIS 项目文件。重新打开远端项目后，确认图层、矢量编辑成果、处理结果、样式及项目状态均正确保存。
整个工作流程中不需要用户切换至 Windows 操作 QGIS，不需要通过远程桌面控制工作站，也不需要手动下载完整原始遥感影像。
测试报告必须区分已经通过真实环境验证的功能、仅通过模拟测试的功能和尚未实现的功能。
16. 开发执行要求
接收本任务后，首先检查当前项目目录、Git 状态、macOS 开发环境及 QGIS 安装情况。随后调查现有开源项目和 QGIS 官方 API，完成技术选型、依赖兼容性分析及总体系统设计，并将相关内容写入 docs/。
在技术调研基础上建立项目骨架，制定具体的阶段任务，并从 V0.1 开始实际编写代码和运行测试。本任务要求交付可运行的软件实现，不能仅提供架构说明、伪代码或静态界面。
优先验证远端连接、文件导入和远程遥感影像浏览，尽早确认项目在实际网络环境下的可行性。每次开发应保持功能范围明确，避免在核心工作流尚未完成前引入大量非必要模块。
代码应当具有清晰的模块划分、类型标注、必要的注释、结构化日志、异常处理及可维护的接口定义。不得使用大量临时补丁、重复实现或未经验证的 API 拼接来维持表面上的功能完整性。
当存在多种技术路线时，优先采用成熟、稳定、便于跨平台部署、依赖较少且能够充分复用 QGIS 原生能力的方案。涉及重要架构调整时，应记录选择依据、替代方案及修改范围。
开始执行项目初始化、技术调查、环境检查和 V0.1 开发工作。
